## 0. 接手用法

1. 先读工作区根agent.md、仓库AGENTS、执行状态；不要仅凭聊天摘要。
2. 核对工作树与当前owner，选择依赖通过且额外门槛满足的一张卡。每次只领取一个会修改共享文件的任务。
3. 将任务改in_progress，填写owner、开始时间、run_id、准确输入版本。若发现其他Agent占用同文件，先交接，不覆盖。
4. 执行卡内范围；一个困难任务允许中途交接，必须记录最后一个可复现检查点和失败命令。
5. 按[步骤交接模板](STEP_HANDOFF_TEMPLATE.md)保存记录，更新JSON状态、next_action和根agent.md。通过项必须有证据；下一位只重验版本漂移或受影响部分。
6. 换Agent后先验证证据路径可读和版本匹配，再继续下一卡；不依赖前Agent内存、进程ID常量、未记录环境变量或聊天口头保证。

任务状态仅not_started/in_progress/passed/blocked/deferred。诊断卡passed意味着已得到可复现结论，不意味着能力可用；能力状态单独记录available/unavailable/unknown。不要用探针passed绕过后续能力门槛。发布等待批准用blocked+reason=waiting_user_review，不能当失败或自动批准。

## 3. 共同规则

- 范围路径以DailyFlow仓库根为相对基准；Shell路径在../OctoSense。具体新增目录/接口写“拟”，实现前先检查是否已有同类入口。
- `src`是真源，`bundle/main.splash`由tools/build_event_app.py生成。共享生成产物由当前集成owner统一构建，禁止多个Agent同时stamp不同版本。
- 保护Cargo.lock、d3d11、运行时选择器、既有未提交改动及所有个人数据。不得因dirty checkout清理重置。外部更新要核对新HEAD并保留。
- Shell修复使用隔离checkout/worktree并记录基准；应用改动与平台改动分开审查。改kernel/Hub需要明确范围与实际工具能力，不假设修改Shell就足够。
- 人负责实际授权和必要GUI操作；不自动批准，不为测试提高权限。使用合成数据和隔离core，不复制凭据进build证据。
- 每步上限是诊断/取舍闹钟，不是承诺开发工时。到时保存并换诊断/降级卡，不能用剩余发布时间无限攻坚。
- 任何回退先记录绝对目标路径和改动归属，只撤本任务改动，保留失败证据/数据备份；不运行git reset --hard/clean。
- 对外发布/PR/比赛提交按具体审核内容执行；本轮只重写文档，未启动这些任务。Goal保持既有状态，不把本文件当自动调度器。

## 4. 验证命令与证据约定

PowerShell示例从仓库根执行。只读基线命令可直接用；业务测试先读脚本或--help核对实际参数，不能照着尚未存在的测试名字运行。

```powershell
git rev-parse HEAD
git status --short
git -c core.whitespace=cr-at-eol diff --check
python -X utf8 tools/build_event_app.py
python -X utf8 tools/test_official_tool_bridge.py --help
python -X utf8 tools/test_source_bridge_contract.py --help
```

build_event_app会生成产物，只能在实现卡需要时运行，不用于纯文档验收。`hub stamp/check`必须选择兼容的实际路径并记录版本，先看工具帮助；不能使用旧默认Hub验证script-tools-v1。旧VM夹具只能计业务/注入测试，不能算生产包或官方Agent通过。

每个新run写`build/semifinal-202610/steps/<DF-ID>/<run-id>/`，不覆盖旧run。至少含summary.json、commands.txt、失败与成功输出、必要截图/状态哈希。模板见STEP_HANDOFF_TEMPLATE；公开证据另行脱敏挑选，不上传整个build/.local-state。

- **验证方法**：同样重复/更正/墓碑一致；导入输入不可信；无跨App调用则证据写none；Agent真实组织仍需DF-11。把实际命令、输入与退出状态写入本run；工具不存在时先定位，不能伪造通过。
- **产物**：fallback-report.json、导入说明、范围决策；运行证据统一放本卡run目录，源码与文档按允许范围保存。
- **完成门槛**：可供DF-11/13使用的可靠数据后端；明确不是实时多App互通；没有安全/数据损坏问题。
- **失败/回退**：导入也来不及则回到已验收核心任务与技术附件，停止新UI范围；不隐藏缩水。保留失败run，更新blocked/deferred及解除条件；按共同规则只回退本卡变更。
- **交给下一位**：填写模板、状态JSON与next_action；下一候选 DF-11（后端门槛）。必填实际修改文件、版本摘要、证据和剩余风险。

### DF-27 退回已验证核心的交付分支

- **领取条件**：DF-01通过；集成负责人明确route=C并写明放弃的新能力；P0条件分支，60分钟上限。此卡不是默认绕过新产品任务。
- **读入/入口**：官方RC2真实证据、当前候选diff、所有新增未完成任务及依赖。
- **允许改动**：构建入口、候选版本与产品声明、相关回归及状态账本；不删源实验或个人数据。
- **执行步骤**：
  1. 列出未进入发布的新来源/新UI/新Agent链，把对应任务标deferred并记录原因。
  2. 仅隔离本轮未完成入口，保留已验证双ABI/收据修复及用户既有功能，不能整体reset。
  3. 在实际候选重新验证主任务、拒绝、更正读回、重启和诚实失败；与旧证据版本有差异就补受影响检查。
  4. 将新产品方向留在roadmap，提交材料仅描述当前核心与独立消费者技术附件。
- **验证方法**：真实候选与发布声明一致；未接入的工具和UI不出现在演示；受影响业务回归通过。
- **产物**：scope-cut.json、baseline-release-report.json、版本摘要和缺项说明，保存本卡run目录。
- **完成门槛**：最低可交付候选可靠且用户能审查缩水范围；不能声称达成跨App图文目标。
- **失败/回退**：若已验证核心也失效，优先修数据/授权/主任务，停止全部新功能；发布仍受实际验证约束。
- **交给下一位**：DF-20。只有route=C且本卡passed时，DF-20才允许以本卡替代DF-17依赖；不能把被跳过任务标passed。

“代码完成”“真实Agent通过”“UI查看通过”“公开发布”“比赛提交”五种状态分开。四项初赛各25分与75分历史不推导确定加分；贡献需证明真实改善自己的应用。官网来源和评分背景沿用[规则核对](OCTOSENSE_RC2_REVIEW.md)及[比赛计划](SEMIFINAL_PLAN.md)中的固定记录，新规则变化需单独核实。
