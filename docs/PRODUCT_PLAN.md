## 1. 产品定位与想法总结

**DailyFlow 是一个以日历为入口、通过对话整理每天生活记录的个人应用。**

用户用自然语言描述生活，应用从中识别需要记录的事情，保存到相应模块；回看时，以日期把这些事情重新组织起来。记账是第一个重要用途，日记和经期记录是首批并列模块。未来可以增加其他围绕日期持续记录的功能。

这套体验有两个互相补充的入口：

- **说一说，记下来**：减少打开多个表单、选择分类、重复输入日期的操作。
- **选一天，看生活**：通过日历切换关注点，再进入当天记录或模块详情。

日历切换的是同一段时间的不同视角。例如在同一个十月，记账视角显示每日支出，日记视角显示有无日记和摘要，经期视角显示实际记录的日期。切换后保留月份和选中的日期。

### 用户已经确认

1. 产品名为 DailyFlow。
2. 通过个人对话解析记账内容，自动记账、分类。
3. 既有常规记账展示，也有可切换模块视角的日历。
4. 首批考虑日记、记账、经期三个模块，并为以后扩展留下基础。
5. 自动记录原则：**明确内容自动记，含糊再问**。
6. 本轮要求总结、评价、优化和策划；尚未授权编写业务功能。

其余默认值、页面细节和阶段安排均为本文建议，不能当作用户已经确认的实现要求。

## 2. 从 Agent 产品开发角度评价

**建议推进，先验证“少费力地记下来，容易按天找回来”这条闭环。**

它的价值来自输入与回看的连接：对话适合表达，结构化记录适合统计，日历适合回忆。同一句话可以留下两笔账和一段日记，不必分别打开三个页面；日后也能从某一天同时找到消费和生活背景。

但这仍是产品假设，尚未经过用户研究或真实使用验证。功能数量本身不构成优势。

| 角度 | 判断 | 优化建议 |
| --- | --- | --- |
| 使用价值 | 输入门槛低，日期能够自然连接日常记录 | 优先验证记录是否更快、回看是否更容易 |
| 日历定位 | 很适合回忆某一天；查询某一笔账、编辑长文另有更合适的界面 | 保留模块列表、编辑页和基础汇总，让日历承担导航与概览 |
| AI 价值 | 拆分多件事、识别日期与金额、建议分类很有用 | 把模型限制在提出结构化记录，保存和统计由确定规则完成 |
| 自动保存 | 便利，也容易因为误记失去信任 | 每次展示结果、日期与金额；提供逐项修改和撤销 |
| 三模块范围 | 能检验基础框架是否通用，也容易分散开发 | 三个模块先做薄，优先完成记账闭环，再接日记和经期基础记录 |
| 长期扩展 | 共用日期、入口和记录生命周期可以减少重复开发 | 先做内部模块接口，出现真实新需求后再扩展；首版不做插件市场 |

最需要避免的情况是：聊天看起来很聪明，却无法可靠保存；日历很丰富，却找不到具体记录；三个模块各有一套数据，修改一处后其他页面没有更新。

## 3. 首批用户与核心场景

首批验证对象建议就是用户本人：在 Windows 上做个人日常记录，愿意用文字表达，不希望每件小事都填完整表单。移动端随手记录可能更便利，但当前尚未验证运行体验，不计入首版承诺。

### 场景 A：一句话记录多件事

输入：“今天午饭花了 32 元，地铁 6 元，晚上和朋友散步很开心。”

在相关模块已启用时，建议产生：午饭支出 32 元、交通支出 6 元，以及保留原话的日记片段。结果回执显示“已记录 2 笔支出，共 38 元；1 条日记片段”，并允许单独撤销其中一项。

日记片段可关联这次输入产生的账目，但关联不会再生成账目，避免支出被重复计算。只有消费事实的句子默认只记账，不自动生成一篇空洞日记。

### 场景 B：通过日历回看

打开十月日历，选择“记账”，10 月 1 日显示“支出 ¥38”；点选当天，看到两笔账。切换“日记”后仍停留在十月和同一天，打开当天日记，继续写作。

### 场景 C：补记与更正

选择 9 月 30 日，输入框明确显示“记录到 9 月 30 日”。输入“晚饭 28”，缺少已发生消费的语境时先澄清；在明确的补记账模式中可以作为支出记录。输入“昨天晚饭花了 28”时，以输入时当地日期解析“昨天”，并在回执中显示具体日期。

“刚才午饭不是 32，是 30”应更新唯一对应账目；存在多个可能对象时先选择，不能另建一笔 30 元支出。

### 场景 D：记录经期

用户主动启用经期模块后，输入“今天经期开始了”，保存明确的开始记录，并可撤销。首次启用时说明数据用途和对话处理方式。未启用时只提示可开启模块，不默默建立敏感记录。

“是不是快来经期了”属于提问，不生成已发生的经期记录。首版只记录实际情况，不提供排卵、安全期或诊断结论。

## 4. 信息架构与日历体验

建议保留三个主要入口：**日历、记录、设置**。全局“记一笔 / 说一说”随时可用。

```text
DailyFlow
├─ 日历：首页，月份导航、回到今天、视角切换
│  ├─ 总览：记录类型标记 + 当天详情
│  ├─ 记账：每日支出 + 当天账目
│  ├─ 日记：记录标记 / 短摘要 + 日记编辑
│  └─ 经期：实际记录标记 + 当天编辑
├─ 记录：按模块查看完整列表、编辑与基础统计
├─ 说一说：输入 → 记录回执 / 必要追问
└─ 设置：启用模块、默认视角、AI 说明、数据管理
```

桌面端建议采用“月历 + 当天详情”的两区布局。窄窗口下可把当天详情放到下一层；具体布局留给原型验证。聊天面板可以收起，避免占满日历空间。

### 日历设计规则

| 视角 | 每个日期格主要显示 | 点选当天后显示 |
| --- | --- | --- |
| 总览 | 有哪些类型的记录，用少量标记表示 | 按模块分组的当天记录 |
| 记账 | 当日支出总额；收入在详情中分列 | 收入、支出明细及当日合计 |
| 日记 | 有无记录；空间充足时显示一行摘要 | 片段列表、全文与编辑入口 |
| 经期 | 已记录的日期、开始 / 结束标记 | 当天记录及修改入口 |

每个日期格只有一个主要信息重点，详细内容放在当天详情。未记录与明确记录为零要区分，空白日期不能被解释成“这天没有消费”。经期只有开始、没有结束时，显示“结束未记录”，不能把之后所有日期自动宣称为实际经期。

首版做清晰的数字、标记和选中态即可。热力图、情绪颜色、生活轨迹等丰富表现，应在基础可读性和数据可靠性验证后再加入。

## 5. 首版范围

建议的首版默认值：单人使用、本地保存为主、文字对话、人民币单币种。账户体系、同步和语音都可后续讨论。

| 部分 | 首版应包含 | 后续再考虑 |
| --- | --- | --- |
| 公共框架 | 日历与月份切换、日期详情、模块启停、统一新增 / 修改 / 删除、持久保存 | 自定义仪表盘、外部插件、多端同步 |
| 记账 | 收入 / 支出、金额、日期、分类、备注；账目列表；月收支与分类汇总 | 多账户、多币种、预算、银行导入、复杂转账与退款 |
| 日记 | 同一天多个片段、正文编辑、列表与日历入口；保留本人原文 | 富文本、附件、AI 代写、自动长篇回顾 |
| 经期 | 主动启用、实际开始 / 结束日期、备注、修改与删除 | 周期预测、健康分析、症状统计 |
| 对话 | 多事项拆分、日期解析、金额识别、建议分类、明确项自动保存、含糊项追问 | 语音、图片识别、跨应用采集、长期自主 Agent |
| 数据管理 | 保存反馈、撤销、失败恢复、基础备份导出与恢复验证 | 云账号、协作分享、后台自动采集 |

分类先用一组简单默认项，允许修改分类；无法合理归类时保存到“待分类”，不要因为分类不确定而反复打断用户。涉及金额、日期、发生与否、归属对象的不确定性则应澄清。

复杂退款、代付、借贷和转账在首版中明确提示暂不支持对应语义，不悄悄当作普通收支处理。

## 6. 对话自动记录规则

### 保存条件

一次输入依次经历：**理解输入 → 提取候选记录 → 校验字段和意图 → 保存明确项 / 追问含糊项 → 返回结果**。

自动保存依赖可检查的条件：明确描述已发生的事项、必需字段齐全、对应模块已启用、没有与已有记录冲突。不能只凭模型给自己的“置信度 90%”决定保存。

| 输入例子 | 建议行为 |
| --- | --- |
| “今天咖啡花了 18 元” | 自动记支出，显示日期、金额、分类及撤销 |
| “明天准备花 200 买书” | 识别为计划；不计入已发生账目 |
| “这周花了多少钱？” | 查询已有账目，不生成新记录；合计由程序计算 |
| “咖啡十几块” | 追问准确金额，不擅自填写 15 元 |
| “朋友说他买了 500 元的衣服” | 不记入本人的账目 |
| “今天午饭 32 已付款，晚饭记不清多少” | 保存午饭，追问晚饭，分别展示状态 |
| “刚才那条删掉” | 唯一对应时删除并可撤销；多个对象时请用户选择 |
| 网络超时后再次点击发送 | 同一次提交不能产生第二份记录 |

日期采用“明确表达的日期 → 已清楚显示的补记日期 → 今天”的优先级。相对日期以输入时的当地日期解析；用户选择的日期与明确表述冲突时，以表述为准并突出显示结果，不能静默改变目标日期。分别保存事件日期与实际创建时间，支持补记。

### 回执与失败体验

回执直接显示“记了什么、记到哪天、是否保存成功”，不要只回复“好的”。已保存、待确认和失败必须可区分。多条记录可以逐项改动或整次撤销；用户之后已有新编辑时，撤销不能无提示地覆盖新内容。

日记默认保存用户原话或原话片段，禁止自动补写未表达的情节。未来如加入 AI 润色或总结，生成内容须单独标记并由用户选择采用。

模型不可用时保留输入，支持手工记账 / 写日记 / 记录经期；重试前明确哪些项目已保存。解析失败与保存失败要分别提示。记录文本中出现指令，只当作待处理内容，不能改变应用的保存权限或执行外部操作。

## 7. 供开发 Agent 使用的框架建议

这是概念层面的边界约定，数据库、文件格式和组件实现尚未确定。

```text
对话输入 / 手工表单
        ↓
候选记录 → 字段与意图校验 → 必要追问
        ↓
统一记录写入与修改入口
        ↓
日记记录 / 收支记录 / 经期记录
        ↓
日历摘要 / 当天详情 / 模块列表与统计
```

**共享记录基础，保留模块自己的字段和规则。** 各模块共用记录 ID、事件日期、创建 / 修改时间、来源、版本和删除状态；金额分类属于记账，正文属于日记，经期起止与日级记录属于经期。对话原文与生成记录通过来源 ID 关联，不把所有业务信息塞进一个无规则的文本字段。

日历是记录的展示和汇总结果，不是第二套业务数据库。修改账目后，月合计、当天详情和日历数字应一起变化。金额用最小货币单位精确计算，不能用模型生成的合计作为账本数据。

模块需要提供四项能力：记录校验、日历摘要、当天详情、编辑入口。先让三个内置模块共用这一约定；无需预先实现动态加载、插件市场或复杂微服务。

模型接口隔离在解析层，输出结构化候选项；存储层负责去重、写入和恢复。查询先由程序筛选与计算，模型可以协助理解查询，但不能编造账目。保留请求标识和必要版本信息，避免重试重复写入或更正覆盖错误对象。

## 8. OctoSense 可行性与技术前置验证

**已核对的上游事实：** OctoSense 的 `model.complete` 已在 PR #95 于 2026-09-28 合并，提供受权限控制的一次性结构化模型调用；调用本身不带记忆与工具。这适合作为 DailyFlow 解析层的候选。来源：[官方 PR #95](https://github.com/OctoSense-org/OctoSense/pull/95)。

官方 Shell 文档已将该能力列为可用，但应用自带 `AGENT.md`、技能和触发器的完整 Agent 生命周期仍列为规划能力。不能把编写配置文件等同于宿主已运行应用 Agent。来源：[OctoSense AI 服务文档](https://github.com/OctoSense-org/OctoSense/blob/main/docs/ai-services.zh-CN.md)。

**本机尚未验证：** 现有 `my-notes` 已验证 Windows 界面、存储和准入；DailyFlow 尚无程序，也未做真实模型调用。当前 App Hub 固定版本与上游 Shell 文档所用版本不同；独立 `card-host` 能运行 Demo，不代表具备 Shell 注册的 AI 服务。

后续获准开发时，先做一次最小能力验证：在目标宿主中申请正确权限，输入一句消费描述，收到符合约定的结构化结果，并验证未授权、无提供方及请求失败时的行为。确认 Windows 上真实可用后，再确定 AI 接入方式。

若宿主路径不满足需求，再评估受控的自有服务；这会带来数据传输、运行成本和维护责任，应另行选择。不要把供应商密钥写入应用包。手工记录与日历可独立完成，但在真实 AI 闭环通过前，只能称为阶段成果，不能宣称已实现用户要求的对话自动记录。

本轮不升级依赖、不配置模型、不启动收费调用。未来升级必须保留工作区的 Makepad Windows 渲染补丁和其他已有修改。

## 9. 隐私与用户控制

三类记录可能涉及私人生活，控制方式应直接进入产品设计：

- 经期模块主动开启，可独立关闭与删除数据；关闭模块与删除历史数据是不同操作。
- AI 首次使用前说明发送什么、发往何处。解析只取当前输入和必要上下文，不默认附上全部账本、日记或经期历史。
- 同一句输入可能包含多个领域的信息；首次说明整句可能被送去解析。用户不愿发送时，可使用手工入口。
- 总览可以隐藏敏感模块标记；备份导出前让用户选择模块并明确包含的数据。
- 本地保存不自动等于加密。未实现并验证之前，不承诺“端到端加密”或“所有数据绝不离开设备”。

原始对话若被保留，应可以删除；删除原文是否同时删除派生记录，应让用户清楚选择。日志和错误报告避免写入完整私人内容。基础备份需要包含格式版本，并做恢复验证，不能只有一个无法读回的导出按钮。

## 10. 分阶段落地与验收

按闭环交付，不在当前信息不足时承诺工期。以下是建议顺序，开始实现仍需用户明确指令。

| 阶段 | 交付成果 | 进入下一阶段的条件 |
| --- | --- | --- |
| 0：产品与能力验证 | 首页、日期详情、对话回执原型；宿主模型能力验证 | 用户能理解记录与回看的路径；明确真实 AI 接入条件 |
| 1：共享基础与记账 | 日历、手工收支、账目列表、月汇总、保存 / 更正 / 撤销 | 重启数据仍在，各页面合计一致，历史补记正确 |
| 2：模块扩展验证 | 日记、经期的基础记录及视角切换 | 三模块共用日期与写入机制，关闭模块后入口行为一致 |
| 3：对话闭环 | 真实解析、多事项记录、澄清、修改、去重与失败恢复 | 对话结果真正持久保存；异常情况下不误报成功 |
| 4：个人试用与整理 | 数据备份恢复、Windows 视觉验证、连续使用反馈 | 主要记录任务顺畅，再决定是否准备发布 |

### 关键验收场景

1. 一句话产生两笔支出和一个日记片段；支出合计正确，日记关联不重复记账。
2. 切换日历视角不丢失月份与选中日期；从详情能编辑对应记录。
3. “昨天”、跨月补记、临近午夜输入都使用可解释的事件日期。
4. 计划、提问、引用别人的消费不会直接进入本人账本。
5. 更正、删除、撤销和网络重试不造成重复记录或错误覆盖。
6. 模型超时后可手动完成；保存失败不会显示“已记录”。
7. 经期模块未开启时不自动创建记录；结束日期未知时不生成虚假历史。
8. 应用重启、备份恢复后记录与合计一致；窗口缩放与冷启动下控件完整。

建议先整理约 50 条自用语料，覆盖正常输入、歧义、否定、计划、日期边界、修改和重复发送。记录字段正确率、误保存数量和完成耗时；这些是待测指标，当前没有测试结果。预置用例中的金额 / 日期正确、误保存为零、重复写入为零是发布门槛，不能据此保证所有真实输入永不出错。

之后连续试用 7 天，观察：是否更愿意记、是否经常需要修正、日历能否找回想找的内容、哪些模块实际被使用。根据问题调整范围，再讨论复杂统计和更多模块。

## 11. 后续扩展与待定项

日后可以加入心情、运动、睡眠等按天记录模块；新增模块应说明自己的记录字段、日历摘要及编辑方式，复用已有日期和保存机制。跨模块总结须基于真实记录，不能从相关性推断健康或消费原因。

下一轮最值得确定的是：首版是否接受 Windows、文字输入、单币种和本地保存的建议；初始首页选总览还是记账；日记片段如何组织成当天阅读页。AI 提供方与宿主方案等到能力验证后再定。

**当前交付边界：** 本文及项目交接文档已经建立。尚无 DailyFlow 页面、数据实现、AI 接入、功能测试或发布包。推荐下一步先评审四个页面的低保真原型：日历首页、当天详情、对话记录回执、模块编辑页。

## 12. UI 原型（2026-10-01 增补）

本节为原型阶段产出，仅描述界面与交互，不包含实现代码。原型确立后才会进入编码阶段。详细 ASCII 图见 `DailyFlow/docs/UI_PROTOTYPE.md`。

### 12.1 设计核心

- **OctoSense Agent 作为统一入口**：始终在线的对话层，接收自然语言输入并解析为结构化卡片，按目标模块路由到对应 App。
- **共享日历作为基础设施**：日历是统一的时间索引视图，供各功能 App 复用，不再按 App 拆分为独立日历。
- **App 作为独立模块**：每个功能模块（记账、日记、经期）拥有自己的数据、列表与详情；App 之间通过日期互通。
- **日历显示受用户控制**：默认显示干净日历；App 标记必须通过显式设置才出现在日历上。

### 12.2 五大界面

| 编号 | 界面 | 用途 |
| --- | --- | --- |
| 1 | 对话视图（默认） | Agent 对话 + 卡片生成 + 输入框 |
| 2 | 干净日历视图 | 仅日期网格与月份导航，无任何 App 标记 |
| 3 | 勾选后日历视图 | 根据用户在设置中勾选的 App，显示对应标记 |
| 4 | App 内部视图 | 进入具体 App 后的列表 / 编辑界面 |
| 5 | 设置面板 | 日历显示开关、模块启停、AI 说明 |

### 12.3 日历显示原则（重要）

- **默认无标记**：日历首次打开或重置后，仅显示日期网格，不展示任何 App 数据。
- **显式开启**：App 标记需要在设置面板中逐项勾选后，才会在日历日期格内显示。
- **细粒度独立**：每个 App 独立开关（记账 / 日记 / 经期），互不影响。
- **动态视图选项**：日历的视图下拉菜单只列出用户已勾选的 App + 「干净」选项；未勾选的 App 不会出现在下拉菜单里。
- **数据可见性**：App 数据本身始终存在并可访问；只是不在默认日历上"被看见"。点击日期进入详情仍可见。
- **隐私优先**：经期等敏感数据应默认不显示在日历，需要用户主动勾选才可见。

### 12.4 三个关键交互闭环

**闭环 1：对话 → App → 日历同步**

1. 用户在对话视图输入"今天午饭 32 元，地铁 6 元，散步很开心"。
2. Agent 解析为 3 条候选记录（💰午饭 ¥32、💰地铁 ¥6、📝日记片段）。
3. 用户确认保存。
4. 卡片分别写入记账 App、日记 App。
5. 在日历的"汇总视图"（需勾选多个 App），15 日格子显示 💰📝 标记。
6. 切换到"记账视图"（需勾选记账），15 日格子显示 ¥38。

**闭环 2：日历 → 视图 → App 进入**

1. 用户从底部导航点击 [📅日历]，进入干净日历视图。
2. 通过设置勾选 💰记账，日历切到记账视图，15 日格子显示金额。
3. 点击 15 日 → 弹出日期详情浮层，显示当日所有 App 数据。
4. 点击 [→ 进入记账 App] → 进入记账 App 内部界面。
5. 左侧日历自动聚焦为记账视图，右侧显示账目列表与编辑入口。

**闭环 3：App → 编辑 → 日历回写**

1. 在记账 App 内部编辑账目金额。
2. 数据更新。
3. 返回日历，金额与标记自动同步。
4. 关闭详情浮层回到日历主视图，状态保持。

### 12.5 与第 4、7 节的关系

- 第 4 节原有"日历 + 当天详情"布局思想保留，但"视角切换"改为"App 入口"——日历视图仍可切换显示内容，但切换对象改为已勾选的 App。
- 第 7 节的数据流增加一层 **Agent 卡片路由**：对话原文先被解析为带目标 App 标签的结构化卡片，再走原校验与写入流程。
- 「明确内容自动记，含糊再问」的规则继续生效，详见第 6 节。

### 12.6 原型尚未覆盖的事项

- 移动端布局（首版仅承诺 Windows 桌面）。
- 暗色 / 高对比度主题。
- 富文本日记编辑器（首版仅纯文本）。
- 多账户、多币种切换 UI。
- 备份恢复流程的可视化向导。

以上均列为后续版本议题，不在本原型范围内。
