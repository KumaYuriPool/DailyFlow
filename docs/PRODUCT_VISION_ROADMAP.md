## 2 产品定位与价值

**DailyFlow 是以日历为入口的个人时间记录与行动系统。** 用户可以围绕一天查看不同事情，也可以围绕一件事跨越多天查看发展过程。

记账、日记、经期、宠物照护、持续新闻都具有时间属性，但业务规则不同。DailyFlow 为它们提供共同的时间表达、关联关系和操作入口，让用户在回看与处理事情时少做重复查找。

产品的核心价值有三项：

- **容易记录**：用一句话或简短表单留下可查证的记录，并能更正与撤销。
- **容易找回**：从日历、主题 Flow 或自然语言问题找到同一批数据。
- **容易行动**：从摘要卡片打开对应记录、完成待办、修改计划或处理提醒。

首批验证对象建议为用户本人，以 Windows 本地使用为起点。移动端、多端同步、协作与商业化都属于后续议题，不计入第一轮承诺。

## 3 核心概念

| 概念 | 定义 | 示例 |
| --- | --- | --- |
| 事件 Event | 某件事在时间上的统一表达，包含摘要与来源引用 | 一笔消费、一次新闻进展、一次经期开始记录 |
| 时间 Time | 表达时间点、日期、区间及其精度 | 10 月 2 日全天、14:30、尚未结束的旅程 |
| 关联 Relation | 连接事件、标签、Flow 和业务记录 | 同属旅行、引用原新闻、由任务完成产生 |
| Flow | 可命名、查看、更新、隐藏、归档或删除的一组事件及组织规则 | 新闻 A、十月旅行、宠物照护 |
| 入口 Entry | 指向处理记录的模块或 App，以及具体记录和操作 | 打开账目详情、编辑经期开始日 |
| 任务 Task | 尚待完成的事项，有到期时间与完成状态 | 明天给猫洗澡 |
| 规则 Rule | 在时间到达或数据变化时检查条件并执行动作 | 月支出首次超过预算时提醒 |

**时间线是 Flow 的一种展示方式；Workflow 是事件从输入到处理、展示和行动的过程。** 一组按时间排序的事件可以形成时间线，加入更新来源、规则和动作之后，才具备自动工作的流程。

### 标签与 Flow 的关系

同一个标签可以直接生成一条 Flow，但标签和 Flow 建议分开保存。标签描述事件的属性，Flow 还包含名称、显示设置、更新来源和提醒规则。

例如，带“宠物”标签的事件可以组成宠物 Flow；“十月宠物支出”则进一步限制月份和事件类型。用户也能手动添加事件或排除不相关事件。一个事件可以属于多个 Flow，成员关系不复制原始账目，也不让金额重复计入统计。

### 时间的表达

发生时间与收录时间分别保存：今天导入去年的新闻，应落在去年的时间位置；今天补记昨天的消费，应计入昨天。

建议支持时间点、全天日期、已结束区间和开放区间。未知时间保留未知，不伪造精确时刻。日历显示时考虑时区；“今天”“明天”按输入时的当地日期解析，并在回执里显示具体日期。

任务到期不等于已经完成。经期只记录开始而未记录结束时，也不能把未来日期自动写成已发生事实。

## 4 核心使用场景

### 日常记录与日历回看

用户输入“今天午饭花了 32 元”。记账模块校验并保存账目，向公共层提供事件摘要，日历与相关 Flow 更新。回执显示日期、金额、保存状态，并提供修改和撤销入口。

用户从日历进入账目详情，修改金额后，账本、日历摘要和卡片展示同一份更新结果。金额合计由程序计算，模型不负责账本运算。

### 经期对话卡片

用户输入“我今天生理期来了”。在模块已主动启用、日期明确且没有冲突时，保存本次开始记录，关联到经期 Flow，并返回“已记录”卡片。

卡片提供修改日期、补充备注、撤销和查看记录。若存在尚未结束的同一次记录，优先识别重复输入；无法确定是更正还是新的记录时再追问。首版记录实际情况，不自动生成预测或诊断。

### 持续新闻时间线

用户创建“新闻 A”Flow，提供文章或选择后续支持的来源。系统提取有来源的事件及发生时间，按时间组织；新报道中重复的信息合并，真正的新进展追加。

每个节点可以打开原文。报道时间、事件时间与不确定表述需要区分；后续更正应关联原节点，不能静默把不同报道的冲突合成为确定事实。第一轮先用人工导入的材料验证结构，持续自动采集后置。

### 预算超额提醒

新增或修改账目后，程序重新计算本月支出。首次从限额以内跨到限额以上时生成提醒，显示已支出、预算和差额，并提供账单入口。

同一超额状态持续存在时不重复刷屏。后续可增加用户选择的分级阈值。Agent 可以解释哪些支出导致变化，但解释应能回到实际账目。

### 宠物照护任务

用户输入“明天提醒我给猫洗澡”。系统创建宠物 Flow 下的待办，显示具体日期；提醒时刻不明确时询问，或使用用户已经设置的默认值。

到点提醒提供完成、延期和打开任务。用户点击完成后，保留任务与实际完成时间的关联，未来可以查询“上次什么时候洗过澡”。本文仅举例记录用户自己的计划，不预设照护频率。

### 跨模块组织

用户说“把这次旅行的支出、日记和行程整理在一起”。Agent 提议 Flow 的时间范围和关联事件，用户可以移除不相关项。原记录仍归各模块管理，Flow 提供统一阅读与进入详情的入口。

## 5 产品界面与卡片入口

建议采用四个主要入口：日历、Flow 列表、对话、模块与设置。日历是默认主入口，对话负责快速输入和查询。

| 界面 | 用户主要完成的事情 |
| --- | --- |
| 日历 | 选择日期、查看当天事件、切换可见 Flow、进入详情 |
| Flow 列表与详情 | 创建主题、阅读时间线、管理成员、来源和更新规则 |
| 对话 | 记录、查询、更正、请求整理，并接收操作回执 |
| 专业模块 | 管理完整业务数据，如账目列表、日记正文、经期记录 |
| 设置 | 控制可见性、模型使用、提醒时段、备份和数据管理 |

日历延续“干净优先”的设计：默认不堆叠所有模块标记，用户选择哪些 Flow 显示。切换视角保留月份与选中日期；复杂内容进入当天详情。敏感标记和通知摘要可以单独隐藏。

### AppCard 与 glance

从用户体验理解，AppCard 承载通过对话得到的交互卡片，glance 承载 App 发布到 Shell 独立信息面板的卡片。两者不是首次展示与后续反馈的前后关系：记录、修改与反馈可以一直留在同一对话中。

同一条记录可以在两个位置展示，并调用同一套业务操作。glance 发布还可以请求通知；通知负责引起注意，卡片展示信息和操作。AppCard 和 glance 底层接入不同，需要各自适配。

第一版 DailyFlow 可以先使用自己的对话界面和固定卡片模板。应用内卡片完成不等于 OctoSense AppCard 已接通。宿主卡片接入是单独的验收项。

## 6 统一协议草案

以下是建议的协议边界，尚非已实现或冻结的接口。

### 公共事件与专业记录

专业模块持有完整业务记录，公共事件保存时间、摘要、来源和操作引用。专业记录是业务事实的权威来源，公共事件是可重新生成的展示与查询结果。

| 字段组 | 建议字段 | 作用 |
| --- | --- | --- |
| 身份 | schema_version、event_id | 支持演进并稳定识别同一事件 |
| 来源 | source_app、source_record_id、source_revision | 定位业务记录，识别更正与同步版本 |
| 内容 | event_type、title、summary | 统一展示，不要求所有模块共用业务字段 |
| 时间 | time_kind、date 或 start_at/end_at、timezone、precision | 表达不同时间形态；开放区间允许结束未知 |
| 生命周期 | created_at、updated_at、status | 区分创建、更新和删除状态 |
| 关联 | tag_ids、关系记录 | 连接主题、其他事件与来源证据 |
| 操作入口 | target、record_id、action | 在当前 App 内路由，未来可适配外部 App |
| 展示控制 | visibility、sensitivity | 控制日历、卡片和通知展示范围 |

Flow 单独保存 flow_id、名称、人工成员、筛选条件、排除项、来源配置与显示设置。系统计算有效成员后按 event_id 去重。提醒规则引用 Flow 或模块查询，而不是把每条提醒规则复制到所有事件中。

第一轮示例：一条账目记录保存金额、币种和分类；对应 Event 保存“午饭支出 ¥32”、发生日期及账目引用；它同时属于“十月支出”和“旅行”Flow；Entry 指向记账模块的该条记录。金额计算仍读取账目原始数据。

### 写入与更新规则

1. 手工表单、对话和卡片共用业务写入接口，先校验再保存。
2. 使用请求 ID 防止重试重复写入，以来源记录 ID 识别同一业务对象。
3. 保存成功后生成或更新公共事件；公共展示失败时记录待同步状态并允许重建，不能悄悄生成第二笔账。
4. 专业记录更正后更新所有相关视图；旧版本请求不能覆盖新修改。
5. 多事项输入逐项显示成功、待澄清或失败，保留未保存内容。

这些规则是第一阶段需要验证的能力，不预设当前 JSON 文件存储已具备事务机制。具体存储形式在能力验证后选择。

### 入口规则

入口描述“目标模块或 App、具体记录、动作”。首版在脚本应用内实现模块查看和编辑。外部跳转仅在宿主已有公开接口支持时，通过应用侧脚本适配并验证；不新增 Shell 路由服务。

目标未安装、记录已删除或缺少授权时，展示可解释的不可用状态，保留摘要和返回路径。不能仅证明 App 被启动，就认为已打开指定记录。

### 删除与归档规则

建议将隐藏、归档、停止自动更新、删除 Flow 和删除原始数据分开处理。

- 隐藏只改变日历展示；归档保留历史；停止更新只停止后续采集与该 Flow 的自动规则。
- 删除 Flow 默认删除组本身、成员关系及其专属规则，保留源记录和其他 Flow 的引用。
- 如果用户希望连组内数据一起删除，先列出涉及来源与被其他 Flow 使用的记录，通过所属模块执行删除。
- 删除源记录后撤下其公共事件或保留适当删除标记，失效提醒不能继续触发；撤销也不能覆盖之后的新编辑。

这个默认值仍是产品建议，需要在原型中让用户验证是否符合直觉。

## 7 自动化与 Agent 分工

建议的工作过程为：输入或数据更新 → 提取候选事件 → 校验并保存 → 更新 Flow 与日历 → 检查规则 → 发布卡片或提醒 → 用户处理 → 结果回写。

| 责任 | 由谁完成 | 原因 |
| --- | --- | --- |
| 理解自然语言、拆分多事项、提出关联 | Agent | 处理表达差异和语义 |
| 保存、金额合计、权限检查、去重 | 业务程序 | 结果需要确定且可复核 |
| 到期检查、阈值判断、重试与补发 | 调度器与规则引擎 | 避免依赖模型持续在线 |
| 解释变化、总结进展、提议下一步 | Agent | 在已有事实基础上提供帮助 |
| 决定可访问数据和自动执行范围 | 用户设置与应用策略 | 保持可控制、可撤销 |

Agent 的接入除了数据格式，还需要明确操作接口：查询事件、读取源记录、创建和更正记录、管理 Flow 成员、创建任务、修改提醒、打开记录。写操作始终经过模块校验。

首版采用固定卡片模板，Agent 输出结构化结果。开放生成任意界面的能力后置，以便先验证数据和动作可靠性。处理新闻正文时，将正文中的指令视作来源内容，不允许它改变记录权限或操作范围。

### 提醒的可靠性等级

| 等级 | 可以承诺的体验 | 验证要求 |
| --- | --- | --- |
| 应用内检查 | DailyFlow 运行时检查预算和到期任务 | 前台实际触发、重复输入不重复提醒 |
| 恢复后补偿 | 重新打开 DailyFlow 时识别错过的任务 | 重启后任务仍在、补发去重 |
| 后台提醒 | DailyFlow 关闭后仍可到点通知 | 宿主或系统调度真实可用，验证关闭与重启 |
| 跨设备提醒 | 多设备保持任务和提醒一致 | 同步、时区变化、冲突与重复通知控制 |

设备休眠、断网和关机影响提醒送达。产品应展示实际支持的等级；前两级通过不能宣称后两级完成。用户可设置安静时段、优先级、延期与关闭规则，避免提醒变成持续打扰。

## 9 MVP 范围

本文建议将第一版定义为“单 App 内可连续使用的时间 Flow 验证版”。

| 纳入 | 完成边界 |
| --- | --- |
| 动态日历与 Flow 时间线 | 正确年月、日期选择、基本过滤和详情入口 |
| 统一协议与模块边界 | 事件 ID、来源引用、时间表达、更新与删除一致性 |
| 记账和经期薄模块 | 必要的新增、查询、更正、删除与保存反馈 |
| 通用任务与提醒 | 完成、延期、运行时触发和重开补偿 |
| 新闻 Flow 样例 | 人工导入带来源材料，验证事件提取与关联 |
| 对话与固定操作卡片 | 真实模型解析、明确项保存、歧义追问、失败保留输入 |
| 数据管理 | 重启读回、基础导出与恢复、敏感显示设置 |

日记基础模块安排在上述链路稳定后的下一阶段；旧产品规划中的首批方向保留。MVP 暂不承诺自动追踪所有新闻、跨 App 工具调用、宿主 AppCard 接入、后台准时通知、多端同步、经期预测和开放插件生态。

## 10 Roadmap 与阶段验收

按能力门槛推进，不先承诺日期。M0 到 M4 构成建议 MVP；M5 起逐步扩大使用范围。M0 可做宿主小实验，但宿主功能正式交付仍需完成 M6 对应验收。

| 阶段 | 目标与主要交付 | 通过后才能承诺什么 |
| --- | --- | --- |
| M0 协议与能力验证 | 明确字段、删除语义与模块接口；用消费、经期、新闻、任务四类样本验证；做最小模型和卡片实验 | 协议能表达不同领域；各宿主能力有明确通过或缺口记录 |
| M1 时间基础 | 单 App 骨架、真实月历、Flow 管理、人工事件与内部入口、基础持久化 | 从日历和 Flow 打开同一记录，更正和删除在两处一致 |
| M2 专业模块 | 记账、经期、通用任务；业务记录投影为公共事件；敏感模块开关 | 三类业务各自校验，共用时间层，重启数据与汇总一致 |
| M3 对话与卡片 | 真实模型提取、固定卡片、保存回执、更正与撤销、重试去重 | 一句话真正写入数据，模型失败时仍能手工完成 |
| M4 自动化与个人试用 | 预算规则、到期检查、重开补偿、备份恢复；连续试用 7 天 | 在明确的运行条件内可靠提醒，MVP 形成完整证据 |
| M5 持续 Flow 与回顾 | 日记模块、用户选择的新闻来源、定期获取、去重更正、跨模块检索和周回顾 | 至少一个持续主题可跟踪，摘要可追溯到真实记录 |
| M6 现有宿主接口接入 | 仅用脚本验证宿主已公开的模型、卡片、路由、Agent 和调度接口；缺失部分后置 | 每个通过实测的适配能力单独开放，不通过新增 Rust 服务补齐 |
| M7 多 App 与生态展望 | 版本化协议与脚本适配规范；跨 App 授权、通信和同步依赖平台已有能力 | 平台提供所需接口后再验证外部 App 接入，当前不承诺实施 |

### 核心验收样例

| 场景 | 必须观察到的结果 |
| --- | --- |
| 真实日历 | 大小月、闰年二月、跨年、星期偏移正确；不固定在 2026 年 10 月 |
| 同一账目出现于两个 Flow | 原始账目只有一条，统计不因重复展示而翻倍 |
| 更正一笔消费 | 账本、日历、卡片与预算结果同步变化 |
| 输入经期开始两次 | 识别重复或要求澄清，不静默新建两次周期 |
| 输入未来计划 | 创建计划或任务，不把尚未发生的消费记入账本 |
| 删除一个 Flow | 其他 Flow 和源记录按约定保留，专属采集与规则停止 |
| 新闻重复与更正 | 重复报道不生成重复进展，时间与来源可查，更正有关联 |
| 超预算后继续记账 | 首次跨阈值时提醒，同一状态不反复刷屏 |
| 任务延期及重启 | 按新时间执行，旧提醒失效；重启后不丢失也不重复 |
| 模型超时或保存失败 | 保留输入，显示真实状态，不出现虚假的“已记录” |
| 卡片打开记录 | 实际进入目标条目；仅打开 App 首页不算通过 |
| 备份恢复 | 记录、Flow 关联、任务状态与汇总一致 |

本表为新方案的拟定验收，不表示当前通过。旧 [ACCEPTANCE_PROMPT.md](ACCEPTANCE_PROMPT.md) 对应 v0.2 单 bundle，不能直接充当本方案报告。

### 试用指标

重点观察记录完成率、误保存数量、重复记录数量、更正次数、找回一条记录所需操作、提醒漏发与重复、有效新闻进展比例，以及模型调用成本。先建立样本基线，再确定数值目标。

预设验收样例中的重复写入和误保存应为零；这只是验收样本门槛，不代表开放输入永远不会出错。连续试用重点回答：用户是否更愿意记录、是否更容易找回、提醒是否有用、自动关联是否需要频繁修正。

### 阶段调整条件

真实模型或宿主能力不可用时，保留手工与应用内验证，不宣称 AI 或宿主接入完成。Splash 容量不足时，在脚本范围内减少同时构造的界面、评估按需呈现或缩减功能；不能自行改用 Rust 或修改运行时来绕过限制。

如果某个外部接入迟迟无法验证，继续推进协议、数据和应用内闭环，并将外部能力单独列为依赖。是否拆回多个 App，应由用户体验和宿主证据决定。

## 11 未来展望

以下为探索方向，尚未进入承诺范围；每项都应先验证用户是否受益。

| 方向 | 用户体验 | 前置条件 |
| --- | --- | --- |
| 个人时间记忆 | “上次搬家前后发生了什么？”串联日记、支出和任务 | 稳定事件身份、可解释关联、来源引用 |
| 自然语言创建流程 | “跟踪这件事，有实质变化再提醒我”生成可编辑的 Flow 与规则 | 已授权来源、可靠调度、规则预览和暂停 |
| 可操作的生活回顾 | 周回顾中直接打开账目、完成任务、延期计划 | 统一操作接口、结果回写、卡片同步 |
| 专题工作区 | 一次旅行、装修或学习计划聚合不同专业模块 | Flow 成员管理、领域适配器、去重统计 |
| 个性化提醒 | 根据用户选择的节奏合并提醒，减少无效打扰 | 明确偏好、反馈记录、安静时段与优先级 |
| 有依据的跨模块洞察 | 分析某次活动相关支出，解释变化并列出引用 | 程序计算、来源可追溯；相关性不当作因果 |
| 多设备连续使用 | 手机上记录，桌面上整理，同一任务只提醒一次 | 同步、离线写入、冲突解决与通知协调 |
| 开放接入协议 | 第三方 App 将摘要和操作入口接入日历 | 协议版本、能力发现、按范围授权与撤销 |
| 共享 Flow | 家庭共同管理照护或旅行，同时保留个人私密记录 | 成员权限、来源归属、审计和退出后的数据规则 |

长期竞争力应来自时间数据的连续性、用户对记录的信任和跨模块行动能力。界面可以变化，模型也可以替换，事件、来源关系与可迁移的协议需要长期保持可靠。

## 12 风险与待定事项

| 风险或待定项 | 建议处理方式 |
| --- | --- |
| 范围扩展过快 | 先完成三条闭环：经期对话记录、预算阈值提醒、宠物到期任务 |
| 专业记录与时间摘要不一致 | 保留权威来源、版本与重建机制，写入走统一接口 |
| 自动关联误判 | 显示关联理由，允许移除和纠正，暂不默认永久改组 |
| 敏感数据进入模型或通知 | 经期主动启用；首次说明模型处理范围；支持最小上下文与隐藏摘要 |
| 删除或撤销破坏其他 Flow | 区分删组、移除成员和删源记录，并检查共享引用 |
| 新闻来源质量和更新成本 | 用户选择来源，保留原文链接、限制频率与调用预算 |
| 平台能力与安装版本不一致 | 每项记录版本、配置、真实运行证据，避免照搬文档结论 |
| 发布准备不足 | 试用通过后再做 listing、真实截图、隐私说明与平台验收 |

实施前最值得确定的是：单 App 验证的具体承载目录、删除 Flow 的默认行为、MVP 是否接受应用内提醒加重开补偿、默认提醒时刻的处理，以及第一批新闻来源。这些不影响本文作为产品讨论底稿，尚未作出的选择不视为用户确认。
